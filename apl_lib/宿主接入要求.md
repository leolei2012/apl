# APL 宿主接入要求

本文面向移植 APL 的嵌入式工程师，约定宿主必须提供的运行条件、硬件接口和存储责任。适用当前 APL 0.3.0 开发版，与源码一起维护。调用示例和首次启动流程见[使用说明](使用说明.md)，完整参数约束见[运行时参数配置](../docs/规格/APL运行时参数配置.md)。接口签名以本版本 `include/apl_core.h`、`include/apl_hmi.h` 为准。

Wi-Fi关闭时不提供`apl_core_get_pid`、`apl_core_set_wifi_connected`，请按`#if APL_COMPILE_WIFI`保护宿主调用。全功能源文件增加`src/apl_wifi.c`；专用参数和状态随模块裁掉，禁止依赖不同构建下的结构体物理布局。详见[模块解耦与裁剪](../docs/规范/APL模块解耦与裁剪.md)。

定时、滤网、产测、记忆、睡眠、风干、氛围灯及各模块均可独立裁剪。对应专用API在关闭后不再声明或链接，宿主按同一宏保护调用；通用ops表的槽位保留但库不会调用已裁掉能力。宿主驱动源文件及回调表内存需由工程师相应裁剪，APL不会改写宿主工程。详见[通用裁剪边界](../docs/规范/APL模块解耦与裁剪.md)。

## 1. 基本运行条件

编译裁剪入口为 `config/apl_build_config.h`，默认保留全部能力。关闭HMI后，`struct apl`不再含hmi成员，宿主负责输入/显示业务并只调用主控接口；所有源文件与宿主须采用相同宏重新编译。开关限制及资源比较见[编译裁剪](../docs/规范/APL编译裁剪.md)。

C51 LARGE 下当前 `struct apl` 默认预留516字节（主控192、人机323、调度余数1），包含PID及内部按键映射；`APL_HMI_COMPILE_KEYMAP=0`移除15字节配置和3字节借用指针，回到498字节。请使用配套头文件重新编译宿主。它不包含宿主驱动、软件栈或中断开销，其他平台的对象大小也不同。测量方法和进一步优化方向见[内存与性能优化](../docs/规范/APL内存与性能优化.md)。

| 项目 | 宿主要求 |
|---|---|
| 实例 | 宿主分配并持有 `struct apl`；不直接访问其内部占位存储 |
| 周期 | 推荐每 `APL_TICK_MS`（1ms）调用一次 `apl_tick_1ms`；内部每 10 次调用执行一个 10ms 业务帧 |
| 执行环境 | 在前台或同一任务串行执行 tick、命令、初始化和记忆恢复；定时中断只记时，输入或其他任务通过队列交给该上下文 |
| 回调速度 | 回调快速返回；驱动耗时操作异步处理，采样回调返回已准备好的缓存数据 |
| 生命周期 | ops 表、上下文和实例在使用期间一直有效；整张 ops 表先清零，再赋需要的成员 |
| 回调重入 | 回调内部不要重新执行 tick、初始化或控制命令；风机回调中可以读取只读目标转速 getter |
| 头文件与编译 | 宿主和 APL 使用同版本头文件共同重新编译；回调按头文件使用 `APL_CALL`，尤其是 C51 |

`apl_tick_1ms` 的分频计数属于各自实例，成功执行 `apl_init` 或 `apl_init_profile` 时清零；初始化后的第 10 次调用才采样按键、推进主控并绘制人机显示。1ms 是宿主调用周期，业务、按键采样和显示更新仍以 10ms 为一帧；2秒自检、3秒长按、5秒预处理和其他业务时长不变。它不是 1ms 电机闭环或显示扫描接口，宿主的 PWM、显示扫描和物理按键消抖仍由驱动负责。

旧 `apl_tick` 保留原来的 10ms 语义；只使用主控或人机时，仍分别每 10ms 调用 `apl_core_tick` 或 `apl_hmi_tick`。同一实例只能选择一种推进方式，不能混调 `apl_tick_1ms` 与 `apl_tick`，也不能在组合对象推进后再推进其中的主控或人机。升级时宿主与 APL 使用配套头文件共同重新编译；冻结 SDK 继续使用自身版本的接口和周期。

APL 计时随调用次数推进，内部不会补偿长时间漏调。若中断记录经过的 1ms 事件，应由前台逐次消费计数，不能用一个布尔标志合并多次事件，也不要在中断里直接调用 APL。宿主不要在一次 tick 中等待串口、Flash 擦写、传感器转换或电机达到目标转速。RTOS 工程应保证周期任务按时运行，GPIO 有效电平和硬件定时器由驱动层处理。

## 2. 哪些接口需要提供

接口需求随产品配置决定，不要求每个产品实现全部外围硬件。下表的“需要时提供”表示：产品启用了对应能力、且期望真实执行或反馈时，宿主必须接入该接口。空回调只能代表未接入，不能据此认为硬件已经工作。

| 类别 | 接口 | 需要时提供的内容 |
|---|---|---|
| 风机 | `apl_core_get_fan_target_rpm`，可配合 `core_ops.set_fan` | 宿主取得当前目标 rpm，驱动电机运行或停止 |
| 加湿负载 | `core_ops.set_pump` | 开关水泵、雾化器等产品指定负载 |
| UV、负离子 | `core_ops.set_uv`、`core_ops.set_anion` | 对应输出驱动 |
| UV 联锁 | `core_ops.get_uv_interlock` | 安全开关闭合返回 1；缺失或其他值按未闭合处理 |
| RGB 氛围灯 | `hmi_ops.set_ambient_rgb` | 设置已经合并亮度的实际 RGB 通道值，详见第 4 节 |
| 蜂鸣器 | `hmi_ops.set_buzzer` | 1 发声、0 停止；响停时序由 APL 决定 |
| 按键 | `hmi_ops.get_key_state` | 填写同一时刻、已消抖的逻辑按键电平 |
| 普通面板灯与数码管 | HMI 的键灯、图标、水位灯、数码管 getter | tick 后读取显示状态，由宿主扫描或写显示驱动芯片 |
| 传感器 | `core_ops.get_pm25` / `get_pm10` / `get_hcho` / `get_tvoc` / `get_humidity` | 选配传感器的最新值和有效性状态 |
| 水位 | `core_ops.get_water_level` | 转换为 `enum apl_water_level` 的离散段位，不传原始 ADC |
| 故障反馈 | `core_ops.get_sensor_status`、`core_ops.get_module_fault` | 驱动或通信层已经确认的状态 |
| 产品身份 | `apl_core_get_pid` | 提供至少17字节输出缓冲；PID随参数配置保存，联网模块按需读取 |
| 运行记忆 | `core_ops.memory_save` 与 `apl_core_memory_restore` | 复制、持久化和恢复运行记忆，详见第 6 节 |

新宿主建议采用 `get_sensor_status` 显式报告状态。旧宿主未提供该回调时，APL 会将已有数值回调视为有效；这个兼容行为不能替代新产品的传感器故障检测。

## 3. 传感器、按键与故障输入

| 输入 | 数据约定 |
|---|---|
| PM2.5、PM10 | 整数，μg/m³ |
| 甲醛、TVOC | 整数，μg/m³；若驱动给 mg/m³，宿主先乘 1000 转换 |
| 湿度 | 整数相对湿度 0～100%；超过 100 的值会被判无效 |
| 传感器状态 | `APL_SENSOR_ABSENT` 未接入、`APL_SENSOR_WARMUP` 预处理、`APL_SENSOR_VALID` 有效、`APL_SENSOR_FAULT` 故障 |
| 按键 | `APL_HMI_KEY_RELEASED` 松开或 `APL_HMI_KEY_PRESSED` 按下；不直接提交短按/长按结果 |
| 模块故障 | `get_module_fault(module, ctx)`：0 正常，非 0 为宿主已确认故障 |

物理按键的 GPIO 极性与消抖在宿主实现；APL 负责短按、长按、组合键、童锁和面板唤醒。`key_event` 是被接受手势的观察通知，不要在其中再执行一次同样的控制。

参数格式v6、定义修订7增加内部按键映射，宿主的上述输入契约不变。固定输入编号仍为 Purify=0、Humidity=1、Timer=2、Light=3、Speed=4、Power=5、Filter=6。启动前先 `apl_profile_defaults`，再按 `#if APL_COMPILE_HMI && APL_HMI_COMPILE_KEYMAP` 填写 `profile.keymap.enabled=1` 和两组动作数组，最后用 `apl_init_profile` 加载并检查返回值，再调用 `apl_link_bind`；组合对象自动绑定自己持有的映射表。`key_event`和键灯getter仍使用原始输入编号，宿主不做第二次映射。默认 Timer+Speed 滤网重置及 Power+Timer 产测组合仍使用原始输入，受原编译开关和状态限制。见[映射示例与生命周期](按键映射.md)。

映射属于产品配置，独立于 `memory_save`。未提供自定义表时使用标准行为；已裁掉或未启用的动作不会执行，动作编号越界会被整表校验拒绝。升级时逐字段解码旧参数为v6默认表后再校验，不可将旧表内存直接当新结构。只使用独立HMI并调用 `apl_hmi_set_keymap` 时，调用方须持有不可变且持续有效的映射表；只在初始化且停止tick时设置，不能使用已经退出作用域的局部表。

每次开机后 APL 为 PM2.5/湿度保留至少 5 秒预处理。5 秒结束并不自动使故障或尚未准备好的传感器有效；宿主需继续如实报告状态。断线、通信超时和过期数据的确认条件由宿主驱动确定，不要用最后一次数值一直冒充有效输入。

温度读取接口当前没有业务使用。没有配置的传感器和模块不会因为回调存在就自动被启用。模块检测回调为空表示无故障反馈能力，不代表已经通过硬件检测。

## 4. RGB 氛围灯输出约定

宿主提供以下 HMI 回调：

```c
void (*set_ambient_rgb)(uint8_t red, uint8_t green,
                        uint8_t blue, void *ctx) APL_CALL;
```

- 每个通道为 0～255，数值已经包含 APL 氛围灯亮度，宿主不再乘一次亮度。
- `(0, 0, 0)` 表示熄灭，`(255, 255, 255)` 表示 RGB 三通道全亮。
- 初始化只建立状态，不调用该回调。第一个 10ms 业务帧末尾同步一次输出（使用 `apl_tick_1ms` 时是第 10 次调用），此后只在最终 RGB 变化时调用；不会每个业务帧重复通知。
- 回调在 HMI 完成本拍显示、自检和屏蔽处理后调用。手动关灯、待机、风干、睡眠熄屏及空气质量输入不可用时，按实际显示状态输出黑色；首次触摸临时唤醒时按 APL 状态恢复。
- 宿主负责 RGB 三通道到 PWM 或灯驱动协议的转换，包括共阳/共阴极性。不得在回调中重新按 PM2.5 判断颜色。
- 回调为空时保留旧 getter 用法：tick 后读 `apl_hmi_get_ambient_color` 和 `apl_hmi_get_ambient_brightness`，宿主自行把每个原始通道与亮度合并；不要把原始颜色直接当作已经调光后的输出。

回调绑定示例，`board_rgb_write` 是宿主驱动：

```c
#include "apl.h"
#include <string.h>

extern void board_rgb_write(void *board, uint8_t red, uint8_t green, uint8_t blue);
static struct apl_hmi_ops hmi_ops;

static void host_set_ambient_rgb(uint8_t red, uint8_t green,
                                 uint8_t blue, void *ctx) APL_CALL
{
    board_rgb_write(ctx, red, green, blue);
}

void host_prepare_hmi_ops(void)
{
    memset(&hmi_ops, 0, sizeof(hmi_ops));
    hmi_ops.set_ambient_rgb = host_set_ambient_rgb;
    /* 再填写get_key_state、set_buzzer；初始化APL时传入同一hmi_ops和板级上下文。 */
}
```

APL 的空气质量颜色为优蓝、良绿、中黄、差红；多个已选空气传感器按既有综合等级确定颜色。正常运行前的数据预处理阶段不亮氛围灯。上电自检 2 秒以及产测全灯显示时，RGB 三通道全亮。纯加湿产品的标准面贴没有这两排氛围灯，无对应硬件时不必绑定 RGB 回调。

目前 APL 按等级直接切换 RGB，没有颜色渐变。Web 仿真作为虚拟宿主，接收同一回调的最终值绘制两排共 30 个灯点，不自己计算等级或设置另一套颜色。

## 5. 风机及其他实际负载

宿主在 tick 后读取 `apl_core_get_fan_target_rpm(&device.core)`，将目标交给电机驱动；0 表示停止。或者在 `core_ops.set_fan` 的输出变化回调中读取该 getter。不要把用户请求档位直接映射成另一套转速，因为自动、恒湿、风干和备用策略可能已经改用了其他实际档位。

APL 给出目标转速，实际转速闭环、起停斜坡、测速、失速和电机硬件保护由宿主电机驱动负责。缺省五档目标为 400/600/900/1200/1500 rpm，导入参数优先；该通用起始值仍需按产品电机确认。

泵、UV 和负离子等输出回调也应快速写入驱动目标。物理负载在复位、启动、停机重初始化和掉电过程中的关闭由宿主保证；不能靠清空 APL 实例关闭仍在工作的硬件。

## 6. 参数表、存储与启动顺序

1. 宿主先把物理负载置为关闭，准备好实例、ops、上下文及调度。
2. 检查持久存储是否有完整、有效且适用于本固件/产品的参数记录，逐字段解码；不要把空白 Flash 强制转换为结构体。
3. 没有导入表时向 `apl_init_profile` 传 `NULL`，采用内置缺省配置；有表时传已解码的 `struct apl_profile`。
4. 检查初始化返回值。非空错误表不会被 APL 静默修正，失败时不能继续对未初始化实例 tick；冷启动需要缺省回退时，宿主先记录错误，再明确传 `NULL` 初始化。
5. 初始化成功后调用 `apl_link_bind`，按需恢复属于同一产品的运行记忆，然后开始每 1ms 调用 `apl_tick_1ms`。初始化已建立自检显示状态，首个 10ms 业务帧同步 RGB 输出。

参数表和运行记忆分别存储。`memory_save` 的指针只用于本次通知，宿主应立即复制结构内容到自己的缓存，再安排后台写入。宿主负责保存记录的版本、完整性、写入寿命和掉电恢复；这些字段和 Flash 地址没有由 APL 定义。

`struct apl_profile` 和 `struct apl_core_memory` 都是 C 内存模型，不能直接作为跨平台串口/Flash 格式使用。选择传输协议后须明确逐字段编码、兼容信息和完整性检查。Modbus 寄存器及实际写入工具目前尚未实现。

收到新产品参数后，宿主应完成停机、物理输出关闭和保存，再按冷启动流程加载。初始化和恢复 API 不可在串口中断中重入，也不是运行中热切换接口。

## 7. 接入验收

宿主接入完成后，在实际板上至少确认以下行为：

- 没有导入表也能完成 2 秒全灯自检、待机和按键开机；首个 10ms 业务帧 RGB 输出全白，自检结束按状态熄灭。
- 1ms 调度不会漏计或重复推进；多个实例分别计时，长按仍为 3 秒；实测最坏业务帧耗时与前台调度余量。
- 开机预处理 5 秒期间氛围灯不伪报空气质量，输入有效后按等级显示蓝/绿/黄/红；异常、关灯和掉电时能实际熄灭。
- 实际风机按 APL 目标 rpm 执行，自动、恒湿、风干和待机均能正确更新目标。
- UV 安全开关、水位、传感器断线等宿主输入与实际负载行为一致。
- 参数和运行记忆分开保存，首次空存储、无效记录、正常保存及保存期间掉电都能按宿主存储策略恢复。

主机回归证明接口与业务输出行为，不能替代上述 MCU 周期、外设、存储和实际负载验证。对应驱动接线、通信超时和产品电机范围由移植工程记录并维护。
