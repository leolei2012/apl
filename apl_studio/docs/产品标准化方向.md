# 产品标准化方向

## 定位

平台面向没有编程能力的产品经理：通过标准能力选择、中文参数与交互规则卡、图形面板和真实业务场景验收定义产品，再生成标准代码库交给软件工程师。产品定义、功能语义、配置、接口说明、验证记录和SDK由同一套输入连接。品类可扩展到风扇、照明、温控、压缩机等，每种新产品族仍需自己的业务模板与验证。

首轮落地纯净化产品经理闭环，操作和验收见[一页手测说明](产品经理纯净化闭环.md)。技术标识与版本由平台管理并保留追溯信息；硬件接入由工程师负责。可视化按任务选择表单、规则卡和面板，不预设必须使用节点图，也不将新增数据字段当成已经实现业务行为。

AP 是第一种业务，独立灯控是检验多品类架构的最小示例。平台不要求所有产品必须有风机、湿度、风干或 APL 头文件。

## 职责

| 层 | 负责内容 | 当前状态 |
|---|---|---|
| 产品模型 | 身份、品类、功能、参数、版本、模板引用 | JSON v1 已实现 |
| 能力描述 | 数据类型、权限、范围、枚举、单位、默认值、依赖 | 模板内声明，已实现 |
| 业务模板 | C 源码、配置映射、API、硬件回调、文档 | AP / 灯控已接入 |
| 平台流程 | 表单、校验、修订、快照、构建、下载 | 已实现 |
| 验证 | 每个模板声明消费程序与实际覆盖范围 | 本机编译 / 执行门禁已实现 |
| 仿真 | 共用时钟、会话与槽位，各产品提供 C 宿主桥接 | AP / 灯控实际 C 程序已接入 |
| 硬件适配 | GPIO、PWM、ADC、总线、存储与 MCU 工程连接 | SDK 给入口，使用方实现 |
| 共享能力目录 | 跨模板复用风机、开关、传感器语义 | 后续阶段 |

灯控只有电源与亮度，使用自己的源码目录、公共接口和消费程序，通过同一配置、保存、构建和下载服务。

## 约定

- 产品标识稳定且工作区唯一；产品修订、模板版本、业务源码版本、目标 SDK 版本分别记录。
- 功能 key、单位、范围、枚举含义、权限和默认值必须完整。不能仅凭相同 key 假定不同品类语义相同，尤其 power 的请求态和实际输出。
- 用户操作、请求状态、实际输出和错误状态应分开描述；实际输出由业务执行或硬件回调确认，数据模型预览不作为输出证据。
- 移植接口说明方向、单位、上下文、生命周期、调用周期与错误约定；模板明确线程 / 中断调用限制。
- 不支持的能力和参数拒绝生成；显式应用模板可规范化草稿，普通保存不能静默丢弃数据。
- 发布版本按目录冻结。更新业务发布新模板版本，旧产品继续绑定旧版本，升级需主动选择。
- SDK 包含真实源码、配置、实际接口、移植入口、示例、验证程序、产品定义与 manifest。用户硬件实现独立于生成目录。
- 编译与消费程序都通过后才能下载，manifest 记录范围和哈希；它不替代目标硬件验收。

现有 apl_studio / apl_sdk_template 目录名、product.apl.json、apl-sdk/ 和包格式标识是兼容名称，不限制产品范围。

## 后续顺序

1. 完成纯净化产品经理试点：标准方案、有限交互、真实C场景验收与中文工程交付；先使非程序员独立走通流程。
2. 根据试点完善能力语义、模式/按键/显示描述及验收覆盖；未确认的湿度规则不设默认业务结论。
3. 再接入真实第二产品，提取实际共用能力并补模板兼容、升级差异与迁移预览，防止升级悄悄改变旧产品。
4. 基于已实现的 AP / 灯控 C 运行桥接扩展产品，后续从同一会话服务接入 MCP。详见 [Web 仿真台](Web仿真台.md)。
5. 按项目增加 MCU / 工具链适配与硬件验证配置，逐步扩展品类。
