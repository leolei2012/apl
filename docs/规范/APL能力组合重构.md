# APL 能力组合与输出边界

2026-10-29。开发源为根 `src/`、`include/`、`config/`。继续使用C结构体、`self`方法和ops注入，能力对象由拥有者持有，不引入堆分配或库内全局实例。净化、加湿等能力可以组合；产品名称只负责选择配置。

## 已有边界和后续方向

`apl.c`已经组合core和hmi，硬件由`apl_core_ops`注入，命令与快照由`apl_type.h`定义。保留这些公共接口、编译裁剪及宿主持有对象的方式。

后续逐项抽取的职责如下；以下能力对象尚未在本检查点完整实现：

| 职责 | 输入与输出 |
|---|---|
| 传感器采样 | 按能力需要读取湿度、空气质量、水位、联锁；已有样本与有效性分开 |
| 净化能力 | 空气质量输入→风速需求及净化输出许可，不查询产品名称 |
| 加湿能力 | 湿度/目标/水位→风速、水泵需求与禁止条件；持有回差状态 |
| 运行与仲裁 | 处理待机、风干、手动、睡眠、极速以及各能力需求的优先级 |
| 执行器提交 | 最终目标→变化去重、对应状态更新、硬件ops回调 |
| 面板配置 | 显式选择按键动作、设置项、显示轮换，逐步替代能力组合推断机型 |

风速表、参与调速的需求、仲裁方式与停泵条件可以表达为策略描述。结构支持配置不代表业务默认值已确定：50%停泵的模式范围、恒湿与风速切换关系、19%恒湿差值归属仍待确认，本次不改变任何策略。

## 第一检查点：私有输出目标与提交边界

仅重构`src/apl_core.c`的输出路径：

```text
原有策略及保护计算 → apl_core_output_targets → apl_core_outputs_apply
```

- `struct apl_core_output_targets`仅存放本拍的风机开关/档位、泵、UV、负离子目标，位于栈上，不加入公开或持久对象。
- `apl_core_outputs_update`保留原有计算顺序：风机目标、恒湿hold更新与泵目标、联锁读取、UV故障/蜂鸣、负离子与UV目标。
- `apl_core_outputs_apply`按风机→泵→UV→负离子提交变化。每次回调前只更新对应执行器的状态；回调读取快照时仍能看到原先的逐项更新时间，不能提前批量提交所有字段。
- 第一拍风机本来停着时不额外调用关机回调；`outputs_valid`仍在提交末尾置位。空ops及空回调保留原行为。
- ops与旧实现一样在联锁getter调用前捕获，提交阶段不重新选择依赖。执行器目标计算后，不改变回调顺序或策略触发时机。
- 未增加机型分支，不改`apl_core_state`、公开头文件、配置、命令/快照/记忆布局、版本宏或冻结模板。

下一步可在该边界前逐项封装能力状态和需求；先用兼容策略保留旧行为，业务规则的变更单独验证，不与结构迁移混在一起。

## 可复现行为对比

固定基线是本地Git提交`749c6fc`，不是由待测代码重新生成的golden。`tests/compare_output_trace.ps1`从该提交读取原core，以相同公开头/配置、编译器和`tests/test_output_trace.c`分别构建基线与工作树实现。若公开头、配置或core之外的组合源码不同，脚本停止要求先检查比较条件。

每个10ms拍和每个回调都记录快照的全部字段、公开电源状态与记忆字段；记录执行器回调参数及顺序。回调内读取快照，不额外推进tick，不比较含填充字节的结构体原始内存。命令返回值与传感器读取也纳入trace。

两个独立对象逐拍交错且交替执行顺序，输入不同。序列覆盖初次待机、运行/自动、湿度和PM变化、睡眠、极速、恒湿达到及回差、缺水恢复、缺水进入风干和结束、UV联锁断开/恢复、定时回调、正常关机、掉电记忆恢复、缺失传感器/输出回调及空ops。

为缩短trace文件，**对比两侧同时**定义风干3秒、缺水转风干4秒、缺水闪烁2秒。它们是隔离测试参数，不修改根配置；原有12组根回归继续使用默认时长。

工程根目录执行：

```powershell
& ./tests/compare_output_trace.ps1
```

脚本只在系统临时目录创建独立文件，输出`report.json`位置；不启动服务、不读写产品数据库、不连接硬件。默认使用已安装的`C:/Qt/Tools/mingw1310_64/bin/gcc.exe`工具链，仅作为C编译器，不运行Qt。其他已安装GCC可以通过`-Compiler`传入，配套需要`size.exe`和`nm.exe`。

## ABI与资源测量

Windows x86_64 MinGW GCC13.1.0，C11、`-Wall -Wextra -Werror -Os`；资源探针使用根默认时长配置，stack来自`-fstack-usage`。比较的是core对象文件的`.text`及编译器报告的`apl_core_tick`静态栈帧，不是包含宿主回调的最坏调用链或MCU实测。

| 能力 | core .text前→后/字节 | tick静态栈前→后/字节 |
|---|---:|---:|
| 净化+加湿 | 4144→4176 | 96→112 |
| 净化 | 3072→3104 | 96→96 |
| 加湿 | 3424→3472 | 80→96 |

- 三种配置的core私有状态均为160字节、对齐8；公开core占位320、hmi1024、apl1344、ops128、snapshot68、memory20字节，前后不变。
- 公共头逐文件不变，`nm`检查导出符号不变；core对象`.data`/`.bss`均为0，没有新增静态RAM。
- 代码段增加32～48字节，tick静态栈增加0～16字节。没有宣称资源零成本；目标MCU工具链的尺寸、栈预算尚未验证，不将宿主数值当成嵌入式上限。
